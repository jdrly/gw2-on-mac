# 0.2 ships KosmicKrisp from my Mesa fork

Decided 2026-11-20. Status: accepted. `arm64` only. Issue #339, a hotfix for #332.

0.2.0 crashes a few seconds after Play on macOS 26. On my rented M1 (26.7.3) and on a player's
M2 Max (26.6), Wine's log ends with `-[AGXG13GFamilyBuffer sparseBufferTier]: unrecognized
selector`. KosmicKrisp, the engine's Vulkan driver (Mach9 0.4.0's
`lib/external/libvulkan_kosmickrisp.dylib`, athei/mesa `d62ee13d18`), asks each buffer for
`sparseBufferTier` behind `respondsToSelector:` when it makes a linear texture on it. On macOS 26
that selector exists only on Metal's base class, `respondsToSelector:` says yes, and the call
throws on every buffer. On macOS 27 it works, which is why my M5 runs the game.

The engine is athei's, and I don't patch his repositories. My app already puts my builds of
`ntdll.so`, `winemac.so` and DXMT into the engine in place of its own. So:

- My Mesa fork jdrly/mesa carries the fix: KosmicKrisp takes a buffer's sparseness from its own
  record of how it made the buffer and never asks Metal (the fork's
  `docs/gw2/adr/0001-fork-and-the-driver-s-own-sparse-record.md`). Its `GW2` workflow builds only
  the driver, the way Mach9 0.4.0 built it, gates it against the engine's file and publishes
  `kosmickrisp-arm64-<commit>.tar.xz` to its pre-release `arm64-builds`.
- `prebuilt.lock` pins that asset (`kosmickrisp_url=`, `kosmickrisp_sha256=`), and
  `scripts/stage-components.sh` stages it into `prebuilt/kosmickrisp` with the same refusals as
  my other builds: another engine or base, a file its `VERSION` doesn't name, no valid signature.
  The Dev build takes the same commit unless `kosmickrisp_commit` names another, and checks the
  download against the digest GitHub reports.
- `gw2om.sh` puts it into the engine whenever the app carries it, with no setting, the engine's
  own kept next to it as `libvulkan_kosmickrisp.dylib.engine`. A switch back to the engine's own
  would crash the game on macOS 26, so there is nothing to choose. The engine's ICD manifest
  stays its own: it names the same path.
- `VERSIONS` names it (`kosmickrisp <commit> <sha256>`), and so do `status`, `session.env` and
  Collect Logs.

## Consequences

- 0.2.1 is the first release with a file of mine outside `lib/wine`. Repair and the engine check
  know its pin (`ENGINE_KK_SHA256`), so a changed or missing file of the engine's own unpacks the
  engine again.
- A Mach9 release with a fixed KosmicKrisp doesn't end this by itself: the next engine move
  repeats the fork's gate against that engine's file, and then I decide whether my fork still
  ships.
- Only a game start on macOS 26 shows the fix works. GitHub's runner has macOS 27, where the
  engine's own works too. The fork's native test there shows my driver never sends the selector
  and gives a linear texture on each kind of buffer.
